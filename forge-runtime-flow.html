一、目前完成的主流程

主流程依序往右，遇到需要人決定時才停下。

AI 05 / 交接

整理已確認的資料

只使用前面確認過的資料，不把同一份來源重新讀一遍。

後面的完整工作

只有確認沒問題，才能交給下一步

資料不夠，或需要你做決定

先停下來等你回答。你回答後，系統會重新找資料或再查一次，不會自動替你選答案。

資料夠了，可以繼續

確認資料足夠後，先關掉前面留下的等待，再把已確認的資料交給下一步整理。

固定流程負責往下走

模型可以理解和提出建議，但不能自己跳步，也不能替人做最後決定。

同一輪只用同一批資料

前面確認過的資料會保留；來源後來變動，也不會偷偷混進這一輪。

每次等待都有自己的編號

每一輪、每種等待和每個決定都有編號，避免舊訊息重開流程或把兩個問題混在一起。

這一輪已完成

  • 需求分流、找檔案、逐項查證與資料交接。
  • 使用者等待、回答、重試、取消與切換。
  • 完成後真正停止，畫面訊息不誤送回模型。
  • 不同輪次的資料分開，舊訊息不能把流程拉回去。
  • Deep Retrieval、Knowledge Understanding 與 Evidence Package 的最小交接；完整 npm test 212/212 通過，npm run check exit 0。
  • Deep Retrieval 與 Knowledge Understanding 的輸出守門：只保留合法工具呼叫，不讓實作內容提前出現。
  • Deep target source 契約與 completion stale termination：缺少 target 時保留重試額度，六個過期 completion 分支都會終止當次流程。

這一輪還沒做完

  • 尚未由使用者在真實 PI session 重跑原始情境。
  • 完整控制面板與固定畫面配置（widget tree、dashboard）。
  • 從多個來源整理摘要、知識卡（Pattern Card）與長期保存。
  • 第二次查核，以及架構文件後面的完整工作，包括外部來源。
  • mixed tool batch 的整批終止行為，以及真實 PI session 的原始情境人工驗收。
  • 不把未完成項目畫成目前已交付。

二、這條流程是怎麼一步步完成的

文件有些是數天合併記錄，這裡保留原日期，不把沒有證據的內容拆成單日。

08/07 至 08/10

先完成骨架、入口與基本畫面

做了什麼：先把工作順序、需求分流、找資料、查證和等待人決定的規則定下來，也接上狀態、訊息和選單。

設計考量：先守住固定流程和人類決策邊界，讓模型只能提出建議，不能自己跳過等待。

實作細節：用集中狀態、訊息和選單接住入口、分流、找資料與等待，畫面先保留最小可操作範圍。

這段期間 Bug：沒有明確記錄的 Bug。當時主要的取捨是先不做完整畫面。

解決方案：先做能看、能操作的基本畫面，避免一開始就花時間做完整控制面板；完整控制面板列為後續項目，等待另案決定。

08/11 至 08/16

查證與等待流程變得可靠

做了什麼：完成查證工具、使用者確認、重試、取消、切換，以及完成遺漏時的復原。

設計考量：等待、重試和取消都可能改變流程狀態，所以必須讓流程可回復，也不能把不完整資料誤當成已確認。

實作細節：把共用檢查放在流程共通位置，依資料是否真的足夠決定阻擋，並讓互動測試有明確結束路徑。

這段期間 Bug：測試有時只是表面通過，測試資料不完整，空資料被錯誤擋下，互動測試也可能一直不結束。

解決方案：改用真正的啟動方式測試，補齊資料，只在真的需要時阻擋，補上共用檢查，並讓測試正常退出。

08/17 至 08/20

保住送出的內容，並正確結束一輪

做了什麼：讓完整查證指令原樣送出，完成後真的停止；畫面和紀錄保留需要看的訊息，但不再誤送回模型。

設計考量：送出的內容和畫面顯示是兩件事；既要保留完整指令，也要用明確狀態表示流程已結束。

實作細節：將原始內容與顯示內容分開處理，加入停止標記，並在重新整理、分支和重新載入時檢查是否還能送回模型。

這段期間 Bug：為了顯示在畫面上而改寫文字，曾讓模型看不到完整指令；把文字藏起來，也曾被誤以為等於流程已停止。

解決方案：移除會改寫訊息的做法，加入明確的停止標記，並在重新整理、分支和重新載入時都檢查內容是否不該送回模型。

08/20 與 08/21 之間

決定從頭開始，逐步確認後再往下走

做了什麼：重新整理開發方式，決定從頭開始，把整條流程拆成一個個小步驟，先確認前一步正確，再推進下一步。

設計考量：08/20 前常發生改好 A 卻弄壞 B，影響是進度無法穩定累積；因此先建立可逐步確認的節奏，讓問題停在剛發生的地方。

實作細節：每一步完成後先做對應確認；通過才往下走，失敗就停在當前步驟修正，不把未確認的變更繼續帶進後面的流程。

這段期間遇到的問題：前面的開發常出現改好 A 卻弄壞 B 的情況，導致修正彼此互相影響，進度無法穩定累積。

解決方案：從頭開始拆成小步驟，每一步先驗證，確認正確才往下一步；如果失敗，就停在當前步驟修正，避免問題一路擴大。

08/21 至 08/22

入口分流與第一階段找資料完成

做了什麼：把規則和使用者文字分開，完成只找檔名與基本資料的第一階段搜尋，每個來源最多列三筆並固定排序。

設計考量：入口分流不能被使用者文字污染；第一階段只需快速找到候選檔案，避免把尚未查證的內容當成結論。

實作細節：分開傳遞規則與使用者文字，對候選檔案固定排序並限制每個來源三筆，再讀取內容確認相關性。

這段期間 Bug：使用者文字可能混進規則裡，讓分流判斷不穩；明明找到相關檔案，系統也曾把它判成不相關；舊測試還會製造假失敗。

解決方案：把規則和使用者文字分開傳遞，真的讀取內容來判斷是否相關，清掉已淘汰的測試並改寫還有效的測試。完整測試最後 140/140 通過。

08/23

先把查證到下一步的交接規則說清楚

做了什麼：確認查證階段負責確認資料和取得人同意，下一步沿用同一份已確認資料，不重讀相同來源。

設計考量：查證和後續整理各自負責不同工作；交接時要保留同一輪的資料，避免來源變動造成前後答案不一致。

實作細節：為每輪、等待和決定保留清楚編號，進入下一步前先關掉舊等待，再把已確認資料交出去。

當天 Bug：這一天沒有經測試證實的新 Bug，主要是在確認可能出錯的地方和交接規則。

解決方案：先決定每一輪、每種等待和每個決定都要有清楚編號，並規定進入下一步前要先關掉舊等待。

08/24

完成交接，並補上最後的 Bug

做了什麼：完成資料分開保存、舊訊息防護、等待前收好舊狀態，並讓正式流程和除錯流程使用同一套檢查。

設計考量：重試、舊訊息、不同等待和來源變動都可能讓流程回到錯的輪次，因此狀態識別必須比顯示文字更完整。

實作細節：以完整輪次與等待編號識別狀態，正式與除錯共用檢查，下一步只讀取前面鎖定的已確認資料。

當天 Bug：重試時可能把「工具還在工作」誤當成「可以重播」；除錯流程可能繞過正式檢查；舊訊息可能重開查證；不同等待可能因編號文字相同而混淆；下一步也可能重新讀到已變動的來源。

解決方案：分開判斷工具是否還在工作和是否真的能重播；正式、除錯共用同一套檢查；在第一次等待前先關閉舊狀態；每輪使用完整編號；下一步只使用前面確認過的資料。

驗證：文件記載為 157/157 測試通過、兩份 tsconfig 的 npm run check 通過，兩輪審查沒有發現問題；本頁沒有重新執行驗證。

08/25

完成 Deep Retrieval、Knowledge Understanding 與 Evidence Package

做了什麼：把更深入的找資料、理解資料和證據交接串起來，讓下一步拿到同一份可核對的證據包。

設計考量：深入搜尋和理解必須分成兩個階段，並保留證據來源、決策、發現與限制；資料不完整或有阻擋性限制時不能假裝完成。

實作細節：每輪用 attemptId + sourceRoundId + phase 組成 identity；重試只更換 attempt，保留原本的輸入與證據。Workflow 依三種結果分流：完成、需要人決定、需要補資料。Evidence Package validator 會檢查查詢數、檔案數、總量、文字長度、重複 ID、引用與阻擋性限制，並套用安全上限。

這段期間 Bug：讀檔後才檢查大小，可能先讀入過大檔案；單筆檢查可繞過整輪 2 MiB 上限；stale outcome 先做其他處理，可能污染目前流程；模型可能覆寫人類決策；active tools 能力消失時仍可能繼續；首次 Grill 轉 Deep 沒有傳 identity，可能讓交接失去這一輪的身分。

解決方案：改成讀檔前先用 stat 檢查大小，並用整輪原子檢查守住 2 MiB；stale outcome 優先驗證後靜默拒絕；先把 human decisions 注入上下文並拒絕重複 decisionId；每次動態檢查 active tools，無法安全限制時 fail-closed；首次 Grill 先建立 pendingReplayInvocation marker，再用 follow-up 傳遞 identity。

驗證：文件記載初次 npm test 208/208，identity handoff 修正後完整 209/209 通過；npm run check exit 0，並有 diff-check 記錄。

解決方案：新增 Deep active 判斷，統一處理串流與終局事件，只清除文字內容並保留合法工具呼叫；因此不必擴大 Grill recovery 或修改 pi-main/。
