一、目前主流程做到哪裡

主流程依序往右，遇到需要人決定時才停下。

已完成 部分完成 架構要求，尚未完成
01 / 入口

使用者需求

收到原始訊息，保留原文，不先改寫。

AI 02 / 分流

先判斷要不要啟動流程

只做一件事：判斷照原話處理，還是開始這套工作流程。

03 / 找資料

先找相關檔案

先列出可能有用的檔名和基本資料，不急著讀完所有內容。

AI 04 / 查證

逐項查證

檢查找到的資料，確認證據夠不夠，判斷能不能繼續。

AI 05 / 交接

深入找資料並整理

沿用前面確認過的資料，缺什麼才補找，最後整理成可核對的資料包。

AI 06 / 後續

交給後續工作

後面還有背景整理、設計決定、規格、實作、測試與審查，目前尚未全部完成。

只有確認沒問題，才能交給下一步

資料不夠，或需要你做決定

第一次只是資料不足時，系統會先自動再找一次。仍然不足，或需要你做決定時，才停下來等你回答；系統不會替你選答案。

資料夠了，可以繼續

確認資料足夠後，先關掉前面留下的等待，再把已確認的資料交給下一步整理。

固定流程負責往下走

模型可以理解和提出建議，但不能自己跳步，也不能替人做最後決定。

同一輪只用同一批資料

前面確認過的資料會保留；來源後來變動，也不會偷偷混進這一輪。

每次等待都有自己的編號

每一輪、每種等待和每個決定都有編號，避免舊訊息重開流程或把兩個問題混在一起。

二、這條流程是怎麼一步步完成的

文件有些是數天合併記錄，這裡保留原日期，不把沒有證據的內容拆成單日。

先把基本流程接起來

做了什麼：接起「收到需求、判斷是否啟動、找資料、查證、等待人決定」的基本順序，也加上最小可用的狀態、訊息和選單。

這段期間 Bug：沒有文件能證實的新 Bug；當時先把完整控制面板留到後面。

怎麼處理：先交付能看、能操作的基本畫面，避免完整畫面拖住主流程。

08/11 至 08/16

讓查證、等待和重試真的可靠

做了什麼：完成查證、請使用者確認、重試、取消、切換，以及模型漏掉完成動作時的復原。

這段期間 Bug：有些測試表面通過，卻沒有走真正的啟動方式；測試資料也曾不完整，空資料被誤擋，互動測試還可能一直不結束。

怎麼解決：改走真正的啟動路徑，補齊測試資料，把共用檢查集中在同一處，並讓測試結束後確實退出。

08/17 至 08/20

送出的內容不再被畫面改壞

做了什麼：讓完整指令原樣送給模型，完成後確實停止；畫面仍看得到必要訊息，但這些訊息不會再送回模型。

這段期間 Bug：為了讓畫面好讀而改寫訊息，曾讓模型收不到完整指令；只把文字藏起來，也曾被誤當成整個回合已經停止。

怎麼解決：把「送給模型」和「顯示給人」分開處理，加入真正的停止訊號，並確保只顯示的訊息在重新載入後仍不會進模型。

驗證：Forge 132 項測試與 9 項互動測試通過；另有 76 項相關測試通過、2 項略過。

08/20 與 08/21 之間

把工作切成小步，避免修一處壞一處

做了什麼：重新安排開發順序，把整條流程拆成小步驟，每一步確認正確後才往下走。

這段期間 Bug：沒有可單獨核對的新 Bug；當時確認的開發困難是不同修正會互相影響，進度不容易穩定累積。

怎麼處理：每一步先做對應檢查；失敗就停在當前步驟修正，不把未確認的變更帶到後面。

08/21 至 08/22

先判斷是否啟動，再找出可能相關的檔案

做了什麼：把固定規則和使用者文字分開，先只找檔名與基本資料；每個來源最多列三筆，順序固定。

這段期間 Bug：使用者文字曾混進固定規則，讓判斷不穩；找到的相關檔案也曾被誤判為不相關，舊測試還會製造假失敗。

怎麼解決：把規則與使用者文字分開，讀取候選內容後再判斷是否相關，並刪除或改寫已過時的測試。

驗證：互動測試 9/9、完整測試 140/140 通過，程式檢查也通過。

08/23

先訂好查證後怎麼交接

做了什麼：確認前一段負責查證資料和取得人類同意；下一段沿用同一份已確認資料，不重新讀取可能已變動的來源。

當天 Bug：這一天沒有經測試證實的新 Bug，主要是在確認可能出錯的地方和交接規則。

怎麼處理：規定每一輪、每種等待和每個決定都要有清楚編號；交接前先關掉舊等待，再送出已確認資料。

08/24

交接完成，舊訊息不再拉錯流程

做了什麼：把每輪資料分開保存，交接前收好舊狀態，並讓正式操作與除錯操作走同一套檢查。

當天 Bug：重試可能被錯當成重播；除錯操作可能繞過正式檢查；舊訊息可能重開查證；不同等待可能混在一起；下一步也可能讀到已變動的來源。這些問題都會把流程帶回錯的一輪。

怎麼解決：把「工具仍在工作」和「可以重播」分開判斷；所有入口共用檢查；每輪使用完整編號；下一步只使用前面已確認的資料。

驗證：完整測試 157/157 通過，兩組程式檢查通過，兩輪獨立審查都沒有發現問題。

08/25

深入找資料，整理成可核對的資料包

做了什麼：把深入找資料、理解資料和整理證據串起來，讓下一步拿到來源、決定、發現與限制都能核對的資料包。

這段期間 Bug：系統曾先讀檔才檢查大小，整輪容量也可能被拆成多筆繞過；舊結果可能干擾新一輪；模型可能覆寫人類決定；工具已不可用時仍可能繼續；第一次交接也曾漏掉這次工作的編號。

怎麼解決：先看檔案大小，再讀內容；整輪一起計算總量；先拒絕舊結果；人類決定先保存且不可覆寫；工具不足時停止；交接時附上這次工作的完整編號。

驗證：初次完整測試 208/208；補好交接後為 209/209，程式檢查通過。

08/26

找資料時不會提前開始寫程式

做了什麼：讓深入找資料和整理資料的階段只準備證據，不會提早輸出程式碼；接續工作也等到正確編號送達後才開始。

當天 Bug：原本只限制可用工具，沒有一起攔住文字，所以找資料時曾提前出現程式碼；工具也曾太早開啟，導致新的工作編號還沒送到，就先用了舊編號。

怎麼解決：在文字產生途中和結束時都拿掉實作內容，只保留查資料需要的動作；接續訊息真正進入後才開啟下一階段工具，無法安全交接時就先擋下。

驗證：輸出守門的指定測試 9/9 通過；最後完整測試 211/211，程式檢查通過。

08/27

過期結果不再反覆重跑

做了什麼：保留這次工作的編號，等正確訊息真的開始後才使用；交接時也會列出可選檔案，缺少檔名時不會亂猜。

這段期間 Bug：畫面狀態曾比真正的接續訊息更早喚醒模型，讓舊編號先執行，反覆出現「過期結果已忽略」；交接沒列出檔案時，也可能把輸入錯誤誤當成需要人類選擇。

怎麼解決：正確訊息開始前先擋住前一輪的處理動作；交接時列出可選檔案，缺少檔名就要求修正輸入，而且不扣掉重試機會。

驗證：兩批完整測試分別為 212/212、217/217，程式檢查通過。實際操作只完成啟動檢查，原始情境仍未人工重跑。

08/28

無效結果會停止，輸入錯誤可以原地改正

做了什麼：讓六種過期結果都結束當次處理；沒有可選檔案或決定編號重複時，保留同一次工作讓模型修正後重送。

這段期間 Bug：過期結果只有「已失效」狀態，沒有停止訊號；空的檔案清單曾被當成要請人選擇；決定編號重複時，系統也沒有清楚表示可以改正後重送。審查還發現「可以重送」一度套得太廣。

怎麼解決：六個過期分支都補上停止訊號；空清單改成請模型換來源；只有決定編號重複這種錯誤可原地重送，其他檢查失敗仍照原規則擋下。

驗證：前一批完整測試 219/219 通過；後一批指定測試 129/129、本機完整測試 214/214。標準測試當時另有 1 項既有缺檔問題，因此沒有宣稱全部正常。

08/29

同一批工作先收齊，再只接續一次

做了什麼：同一批搜尋和完成結果會先一起收好；純搜尋結束後會自動接續。只用來顯示狀態的訊息不再送進模型流程，需要人回答的畫面則保留。

當天 Bug：搜尋和完成若同批出現，可能互相打架；純搜尋後有時沒有下一步；只想更新畫面的訊息也曾讓模型多跑一輪，造成順序混亂或卡住。

怎麼解決：用每個處理動作自己的編號追蹤整批工作，等搜尋都收齊後只送一次接續訊息；刪除不必進流程的畫面傳送，只保留狀態文字和真正需要人回答的面板。

驗證：指定測試與互動測試通過，實際操作測試最後為 11/11。完整套件當時曾在顯示結果後未退出，程式檢查也仍有上游既有問題，所以沒有宣稱整個工作區全部正常。

08/30

資料真的不足時，先重找，再請人確認

做了什麼：第一次資料不足會自動回頭再找；第二次仍不足才詢問使用者。使用者明確同意後，回答會被記成可追查的使用者前提，再和已查證資料一起交給下一步整理。

當天 Bug：直接送出接續訊息會留下舊的工具清單；等待畫面沒等完就往下走，可能錯過回答；沒有鎖定資料時，合法的補救結果也曾被誤擋。

怎麼解決：先結束舊回合，等它完全停下後再開下一步；等待畫面確實完成後才繼續；把同一工作中已確認的資料保留下來，並清楚標明使用者前提不是外部事實。

驗證：資料包 13/13、流程狀態 22/22、擴充功能 142/142、實際操作測試 12/12、完整測試 248/248，兩輪獨立審查都通過。整體程式檢查只剩未修改的上游 highlight.js 既有問題；Forge Runtime 本身沒有錯誤。

08/31

摘要可以幫人看懂，但不能替正式資料做決定

當天 Bug：測試一開始因完成項目的 schema 括號不平衡，沒有取得有效的失敗結果，無法直接證明新規則真的被測到；本輪未發現新的 Forge Runtime 執行錯誤。

怎麼解決：修正 schema 括號後重新跑有效的先失敗、再通過測試，並確認互相矛盾的摘要不會改變正式 Context Builder 項目；沒有新增第二套資料格式，也沒有修改上游 pi-main/。

驗證：有效測試由 145/1 變成 146/0，Context 單項測試 4/0，完整測試 266/266；規格與標準審查通過。整體程式檢查仍只被未修改的上游 highlight.js 宣告問題擋住。

09/02

取消就完整清掉這一輪，回到最初入口

做了什麼：Deep Discovery fallback 的可見選項改為「確認／取消」，共用畫面仍可選「自行輸入…」；選擇取消或輸入精確的「取消」後，流程會回到 RECEIVE。

這段期間 Bug：原先畫面把「同意」列為可見選項，取消也會保留部分 fallback 資料，無法真正回到乾淨的初始狀態。

怎麼解決：讓 fallback 取消重用完整清理與 sessionState.reset()，清除輸入、證據、標記和目前工作；舊「同意」只保留精確的隱藏相容輸入，一般 deep_decision 取消契約不變。

驗證：session-state 33/33、extension 153/153、真實 TUI 14/14、完整測試 282/282；隔離工作區驗證同樣為 282/282，差異檢查為 0，審查沒有阻擋問題。

09/02

沒有正式規格，也能探索，但不能假稱相容

做了什麼：建立 Spec Gap，讓缺少正式規格時可以做本機實作、模擬與黑箱驗證；每種驗證層級都清楚限制能說到哪裡，正式規格驗證則需要可信來源。

這段期間 Bug：初版驗證器曾放過格式錯誤的 scenarios，錯誤的正式規格引用也可能直接拋出例外；公開的同形狀信任資料還可能被呼叫端偽造。

怎麼解決：所有 scenarios 先確認是字串陣列，正式規格欄位改用安全的非空字串檢查；移除可被偽造的公開信任參數，當前 runtime 的 spec_verified 沒有可信匯入器時一律先擋下來。

驗證：Evidence 專項 28/28、Forge Runtime 完整測試 292/292、程式檢查沒有本 ticket 診斷，差異檢查沒有空白錯誤；可信正式規格匯入、來源綁定與通用高風險操作防護仍未完成。

09/03
